## 第三轮：学习字段与数据结构

### 用户消息 #75
我觉得关于学习的字段类型应该有很多。至少应该包括以下几点：课程、刷题、复习、笔记、背诵、默写。
这些自带类型也应该是根据用户的自然语言描述，自然填入的。其中刷题笔记和默写应该算是输出。
系统最好是能够智能推断，否则让用户自查太麻烦。
理想中的流程就是通过自然语言输入，自动匹配对应进度。比如说我有一个习题册刷到了5.2。
用户又说自己刷了，那根据进度推断，就应该是这本书目录的下一节内容。
不过用户最好还是能够写清楚具体的章节或者自己在对应的进度界面找到对应的内容进行勾选记录。
但是这些作为用户备选项，要设计出来，但是不让用户主动去做这些。

我觉得目录结构肯定不能完全让用户自己建立，不然那麻烦程度简直太高了。
让用户得不偿失。记录半天大部分还都在做一些无用功。但是我觉得内置常见教辅目录又不太可能，因为总有各种奇奇怪怪的教辅。
内置的话肯定还是要有，但是肯定覆盖不够。
所以我有三个主要方向，并且都应该实现出来。
1.通过用户对教辅目录进行拍照，自动采用文字识别识别对应目录，生成相关文件。
2.通过内置的ai（需要用户自行填入api）进行搜索，生成相关文件。
3.用户手动填写目录，系统智能识别章节分布（当然要给用户一定的规范），生成相关文件。
但我觉得这样就只能统计进度，而很难和知识点关联起来，这一点我不知道该怎么实现。
而且我觉得最重要的是除了解决教辅之外，还需要解决网课。网课的话也需要统计进度。

遗忘曲线当然是要的，这个算是anki相当合理的一个机制。
但是我们要相应做出自己的更改和和适应，在它的基础上，还要加入用户的学科时间比例权重。
也就是根据用户过往的数据，推测每天在每科上能用的时间，以及根据用户的偏好和选科等，确定到底应该推荐多少时间，才对他的学习有最大化的帮助。
推荐的内容当然是有上限的，但是这个上限是根据系统计算用户过往，每个任务所消耗的时间来分配的。
比如说用户过往趋势是在周五学习6个小时，并且他的任务a一般消耗60分钟，任务b一般消耗30分钟，任务c消耗40分钟，以此类推。
（这个就需要根据用户的过往任务数据和完成系统推荐任务的数据）
那么，所有推荐的任务消耗时长加起来应该是他在这一天的学习时长趋势时间。

我前面说过了，这个结构继续沿用，但是可能要优化算法，就是能够在缺少一些数据的情况下，也能够把经验归纳到相关的地方，进行整体算法计算。

后续可以慢慢添加各种其他功能。其他功能肯定是要添加进来的，一定要模仿那些已经完成的 app，比如番茄to do这种，或者去网上搜索开源的也可以。
肯定要让用户看到才有成就感。

以下是一些基本的设计规则：
1.1 禁止做的事

· ❌ 禁止使用 WebView 直接加载原网页（除非你明确允许）。
· ❌ 禁止使用 !! 非空断言，必须用 ?.、?: 或提前判空。
· ❌ 禁止使用 GlobalScope，协程作用域必须绑定生命周期（如 viewModelScope、lifecycleScope）。
· ❌ 禁止硬编码像素值，使用 dp 或根据屏幕宽度计算的 LocalConfiguration。
· ❌ 禁止在 @Composable 函数里直接执行网络或数据库操作，必须放到 ViewModel 中。

1.2 必须做的事

· ✅ UI 完全使用 Jetpack Compose + Material 3，不要用 XML 布局。
· ✅ 状态提升：Composable 只负责显示，数据由 ViewModel 通过 StateFlow 提供，事件通过回调上传。
· ✅ 每个屏幕对应一个 @Composable + 一个 ViewModel，通过 hiltViewModel() 获取实例。
· ✅ 网络请求统一用 Retrofit + OkHttp，响应数据用 sealed class 封装成 Loading / Success / Error 状态。
· ✅ 颜色、字体、形状 定义在 Theme.kt 中，遵循 Material 3 动态配色。
· ✅ 导航 使用 Compose Navigation，并且与 ViewModel 的生命周期绑定。
· ✅ 所有耗时操作 必须用协程（suspend 函数），并在 ViewModel 中用 viewModelScope.launch 调用。
